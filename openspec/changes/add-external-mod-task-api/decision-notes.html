1. Pin Tab yes, HUD no decided

You framed this as "even if it's a new pattern" — it isn't. The assignment stamp icon (ScribeAssignedTaskIcon) already works exactly this way today. I checked: HudScribePins.cs builds its own widget tree from scratch and never references IsAcceptedAssignment/AssignerUid/AssignedDate anywhere. The Pin Tab's row widget (ScribePinnedContent/ScribePinRow) is a separate renderer that does read those fields and does build the icon.

                              v
                  ScribePinnedRef  (one shared snapshot,

                  - AssignerUid             versioned pin codec)

                  - AcceptedDate
                              |
              +---------------+----------------+
              |                                 |
              v                                 v
   ScribePinnedContent / ScribePinRow      HudScribePins
   (feeds the Pin Tab)                     (feeds the HUD)
              |                                 |
              v                                 v
   reads IsAcceptedAssignment,             never references those
   renders ScribeAssignedTaskIcon          fields at all — builds its
   + tooltip                               own simpler row, no icon

Both surfaces pull from the same stored snapshot; they just choose different subsets of it to render. That means for ExtraInfo the shape is identical: one new field on ScribeBlock, snapshotted into ScribePinnedRef (one codec version bump — same move as when IsAcceptedAssignment itself was added), read + rendered by the Pin Tab's row widget, and simply never referenced by HudScribePins.cs. No parallel system, no HUD-suppression flag needed — the data exists once, the HUD's own code just doesn't look at it.

Net effect: the cost of "Pin Tab only" is exactly the cost of "Pin Tab + HUD" would have been for the storage side (one field, one codec bump) — the savings are entirely on the HUD's render code, which you skip writing.

2. ExtraInfo length cap decided

Capped to ScribeDocumentCodec.MaxTaskTextLength — the same bound a normal task's own text gets. Clipped, not rejected, matching every other text field's convention (an overlong caller string degrades gracefully instead of failing the whole call).

3. The three-method surface open

Does this three-tier split still feel right, now that provenance collapsed to one opaque string?

TryCreateTask(player, title, bodyText = null)
    -> the trivial case: one task, no stamp icon, no JSON

TryCreateExternalTask(player, title, bodyText, extraInfo)
    -> one task + the new hoverable-info icon
    -> extraInfo is REQUIRED here (a stamp with nothing to show
       would be a contradiction — the method itself enforces the
       pairing instead of a doc comment saying "don't do that")

TryImportTasks(player, documentJson, extraInfo = null)
    -> hands off to the EXISTING ScribeDocumentJsonCodec +
       ScribeImportValidator, for a caller with more than one task
       (a quest mod dumping a multi-step checklist, say)
    -> extraInfo applies to the WHOLE batch, once — it is not
       embedded per-block in the JSON payload (that DTO is shared
       with the human clipboard-export feature; provenance is a
       property of the call, not of the format)

   all three ultimately call one private core method, mirroring
   TryCreate / TryCreateAccepted / TryCreateSent -> TryCreateCore
   in ScribeAssignmentStore today.
OptionProCon
Three methods (above)Each name signals intent; no meaningless parameter combos possible; mirrors an existing in-repo conventionThree things to document instead of one
One method, everything optionalOne signature to learnNothing stops a caller passing extraInfo with no sourceLabel-shaped context to hang it on; harder to see "batch" vs "single" at a glance
Leaning: keep the three-method split. The main open sub-question is naming — TryCreateExternalTask vs. something that reads better next to TryCreateTask (e.g. TryCreateTaskWithInfo?). Cosmetic, but worth a beat before it's public API.

4. Links inside the stripped body text open

A Notice Board notice can contain links (web, handbook, command). What happens to them once the body is stripped to plain text?

(a) subtask-per-link, new "url:" Link flavor
    Depth 0  [ ] Fix the north fence
    Depth 1    "Materials needed, see the board..."
    Depth 1    -> https://example.com/fence-plan      <- new Link kind
                                                          + browser-open handler
                                                          + "leaving the game" confirm

(b) leave URLs as plain text inside the stripped body
    Depth 0  [ ] Fix the north fence
    Depth 1    "Materials needed, see the board...
                https://example.com/fence-plan"        <- visible, not clickable

(c) inline clickable spans inside the body text itself
    Depth 1    "Materials needed, see [the board]"      <- [the board] is a live
                                                             link INSIDE one Text
                                                             block, VTML-lite
OptionNew capability requiredFidelity to sourceRisk
(a) Link subtask per URLNew LinkTarget prefix + external-browser click handler + confirm dialogHigh — each link is a first-class, clickable rowOpening arbitrary external URLs from game content is the first time Scribe would do that at all — needs a trust/confirm story
(b) plain text, inlineNoneMedium — visible, not actionableNone
(c) clickable spans in bodyRich-text-within-a-Text-block renderer (a small VTML-lite span system)Highest — closest to what the notice looked likeBiggest lift by far; touches the shared text-rendering widget every row uses
Recommendation unchanged from before: ship (b) for v1. It costs nothing, and it doesn't foreclose (a) or (c) later — those become easier to justify once a second external caller actually wants clickable links, rather than building browser-opening machinery for Notice Board alone.

But — a wrinkle worth flagging

Notice Board's message-list buttons (bump / pin-parchment / etc.) already prove they're fine building UI affordances on their own side. If they wanted a live link back to the original notice, that's arguably their job to build (a "jump to source" affordance in their own GUI, keyed by a board position they already have), not something Scribe needs to carry. Worth remembering if this comes up again: Scribe doesn't have to solve every fidelity gap — some belong on the calling mod's side of the fence.

5. Server-side item validation for TryImportTasks open

Is this in scope for the first version, or explicitly deferred?

Scriptorium import today:
   client (live registries) --resolves Tracker/Link item codes--> validated doc
                                        |
                                        v
                              server RE-PARSES the JSON
                              (trusts nothing, but does NOT
                               re-run item-code resolution —
                               the client already did that)

External-mod TryImportTasks:
   caller mod (server-side) --???--> Scribe (server-side)
                                        |
                                        v
                              NO client round-trip exists here.
                              Item-code resolution needs a SERVER-
                              side equivalent of ScribeImportValidator
                              that doesn't exist yet.
OptionEffect if an external caller's JSON references an unknown/typo'd item code
Build the server-side validator nowBad references degrade to a plain Task cleanly, exactly like every other import path
Defer — skip validation for v1An unresolvable Tracker/Link either renders broken (no icon/name) or needs a cruder fallback than the existing degrade-to-Task behavior
Given TryImportTasks is the least urgent of the three methods (Notice Board only needs TryCreateExternalTask for its single-notice case), I'd lean toward deferring the server-side validator and the whole TryImportTasks method to a follow-up — ship the two single-task methods first, add bulk import once a caller actually needs it. That also buys time to decide whether the validator logic even belongs duplicated server-side, or whether it should move to a shared Core-callable form used by both paths.
