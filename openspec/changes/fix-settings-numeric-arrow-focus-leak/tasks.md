- [x] 1.2 Add a DEBUG per-frame focus trace (per the banked "settling loops & race diagnosis" method) that logs which `FocusNode`/widget holds focus before and after each write-through rebuild, and capture the exact transition on press #2. — SUPERSEDED by a definitive source read of the LibGUI + VS dispatch path (see 1.3): the transition is fully explained by static analysis of `GuiManager.OnKeyDown`, `GuiBase` per-instance `FocusManager`, and `ScribeDialogBase.CaptureAllInputs`/`OnMyPinsChanged`. No runtime trace was needed and none was added, so 3.5 (remove trace) is a no-op.
- [x] 1.3 From the trace, confirm the root cause. — ROOT CAUSE (from source, corrects the design's three hypotheses which all assumed the leak was WITHIN the settings dialog's own focus manager): the settings dialog and the document editor are SEPARATE `GuiDialog`s, and `GuiBase` gives each its OWN `FocusManager` (GuiBase.cs:140, an instance field). A numeric step calls `UpdateMySettings` → `MyPinsChanged` (ScribeModSystem.ClientPrefs.cs:127), which BOTH dialogs subscribe to. The editor's `OnMyPinsChanged` (ScribeDialogBase.cs:394) re-arms `autoFocusRowOnRebuild` for the still-focused row and `ForceRebuild()`s, which re-`RequestFocus()`es that row IN THE EDITOR'S OWN manager. `GuiManager.OnKeyDown` (VintagestoryLib) runs a FIRST pass over every open dialog whose `CaptureAllInputs()` is true, BEFORE the focused-dialog pass, breaking on Handled. `ScribeDialogBase.CaptureAllInputs()` (cs:478) returns true whenever the focused editor row's `FocusNode.HasFocus` is true — which the editor just re-established. So on press #2 the editor dialog captures Up/Down ahead of the settings dialog and drives the row caret. The numeric registry one-shot is NOT at fault (it re-focuses the field in the SETTINGS manager correctly); the settings dialog simply never gets the key because the editor's `CaptureAllInputs` pass wins first. Fix must stop the editor dialog from CAPTURING the key while a different dialog owns the interaction — i.e. the editor's `CaptureAllInputs`/`OnMyPinsChanged` re-home is the party to scope, not the numeric field.

## 2. Fix focus retention

- [x] 2.1 Apply the minimal fix indicated by 1.3. — DEVIATION from the design's assumed site: 1.3 proved the leak is NOT the settings dialog's re-focus handshake (that works — the numeric field DOES re-focus in the settings manager, with `FocusNode.Owner` already wired in `InitState`, ScribeNumericField.cs:166). The real fault is the EDITOR dialog pre-empting the key via `GuiManager.OnKeyDown`'s `CaptureAllInputs()` first pass while it is not the focused dialog. Fix applied in `src/Mod/ScribeDialogBase.cs` `CaptureAllInputs()`: gated the whole predicate on `Focused`, so an editor that isn't the active VS dialog no longer captures keyboard input ahead of the focused settings window. Left `ScribeNumericField.cs`/`ScribeSettingsContent.cs` untouched — no change was needed there.
- [x] 2.2 Only if the trace shows the editor row is acting on Up/Down without genuinely holding focus, have `ScribeMultilineField` decline focus/keys it was not given; otherwise leave `ScribeMultilineField` untouched. — NOT NEEDED / left untouched: the row DOES genuinely hold focus (in the editor's own `FocusManager`) and its `OnKeyDown` is correctly `HasFocus`-gated (ScribeMultilineField.cs:632). The fault is the dialog-level capture pre-empt, not the row mishandling the key, so `ScribeMultilineField` is unchanged.
